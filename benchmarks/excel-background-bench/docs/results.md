# 計測結果

計測環境: Windows 11 Home 26200 / Excel 16.0 (64bit) / .NET Framework 4.x csc / ローカル NVMe。
データ: 日本郵便 KEN_ALL.CSV (120,682 件) から作った郵便番号→住所辞書。入力は 1,000,000 件。

すべての計測で、日本郵便データの取得時間と 1,000,000 件入力の生成時間は計測範囲外です。
表示はすべて「終了時刻を確定 → 計測値を確定 → 1 回だけ表示」の順で、処理中の
`Application.StatusBar` 更新やシート書き込みは一切行いません。

## 正解の作り方

VBA / C# とは独立に PowerShell で同じ規則を実装し (`build/make_dict_reference.ps1`,
`build/make_input_reference.ps1`)、

- 辞書 120,682 件 … バイト一致
- 出力 1,000,000 件 … バイト一致
- FNV-1a 32bit ハッシュ `22E2C28C` … 設計を 3 回組み直しても不変

を確認しています。「一致」の判定は全 1,000,000 行の突き合わせで、抜き取りではありません。
`該当なし` は 1,670 件で、これも全方式・全実行で同数です。

## 1. 起動手段の比較 (1,000,000 件 / 各 5 回 / 中央値)

Input / Master / Output は同一ブックのシート。Input と Master は各 1 回だけ読み、
Output は `Range.Value2` へ 1 回だけ一括書き込み。完了はワーカーが通知セルを 1 回書き、
Excel 側は `Worksheet_Change` で受けます。ポーリング・固定待機・中間 CSV はありません。

| 方式 | 起動 | 変換 | 処理 E2E (中央値) | 一致 |
|---|---|---|---|---|
| 1 セル単位 VBA (意図的に遅い) | - | 16.9 | 16.944 | 5/5 |
| 2 Dictionary + Variant 配列 VBA | - | 3.15 | 4.082 | 5/5 |
| 3 BAT を手動で開く | 0.39 | 0.05 | 1.396 | 5/5 |
| 4 WScript.Shell.Run | 0.39 | 0.05 | 1.396 | 5/5 |
| 5 VBA Shell | 0.38 | 0.05 | 1.404 | 5/5 |
| 6 タスク スケジューラ COM | 0.40 | 0.05 | 1.420 | 5/5 |
| 7 不可視の別 Excel プロセス | - | 3.27 | 4.664 | 5/5 |
| 8 Shell.Application.ShellExecute | (未解決) | 0.05 | - | 5/5 |

計 40 回すべて全件一致。単位は秒。

方式 8 は起動の中央値が 53.9 秒と他方式から大きく外れており、原因は未特定です。
変換結果は他方式と一致しますが、**起動時間の数値は本ベンチマークの結論には使えません**。
今回は調査対象外として保留しています。

方式 7 の変換 3.27 秒と方式 2 の 3.15 秒の差は 3.9% です。両者は
`modZipRule.BuildDictFromMaster` / `modZipRule.ConvertBlock` という同一の関数を
呼んでおり、辞書・ループ・配列の扱いに差はありません。以前の版で見えていた大きな差は、
別 Excel 側だけが CSV を読んで `Replace`/`Split` していたことによるもので、
両者をシート読み取りに揃えた時点で消えました。

## 2. 結果の届け方の比較 (1,000,000 件 / 各 5 回)

起動手段を `WScript.Shell.Run` に固定し、C# ワーカーが作った 1,000,000 行を
**どうやって前面ブックへ届けるか**だけを変えた 2 方式です。読み込み・辞書構築・変換は
同一コードで、`deliver` 引数だけが分岐します。

- 候補 2 (方式 9) … 一時名 `out_<token>.tsv.tmp` へ書き、完成後に同一ボリューム内で
  `File.Move` (atomic rename)。Excel は `QueryTables.Add` (`TEXT;`, UTF-8/65001,
  タブ区切り, 全列 `xlTextFormat`, `BackgroundQuery = False`) で一括取り込み。
- 候補 3 (方式 10) … ワーカーが COM 経由で `Range.Value2` へ 1 回だけ一括書き込み
  (`string[,]` = VT_BSTR の SAFEARRAY)。

### 読み取り

**候補 3 が E2E で 7.7 倍速い。** ただし内訳は直感と逆になっています。

- ファイル出力そのものは TSV のほうが速い。1,000,000 行の TSV 書き出しは 0.038 秒で、
  COM の一括書き込み 0.822 秒の約 22 分の 1。atomic rename の追加コストは測定限界以下。
- 逆転するのは Excel 側です。`QueryTable` の取り込みが 10.221 秒かかり、
  ここだけで候補 3 の E2E 全体の 7 倍を消費します。ワーカーが速く書けても、
  Excel にテキストとして読み直させた時点で負けます。
- 候補 3 に「Excel 反映」区間が存在しないのは、ワーカーの書き込み先がそのまま
  前面ブックのセルだからです。転送が完了した時点で反映も完了しています。

つまりこの比較で効いているのは I/O 速度ではなく、**Excel の内部表現に入るまでに
何回テキストを経由するか**です。候補 2 は string → UTF-8 バイト列 → パース → セルと
3 回変換し、候補 3 は SAFEARRAY を 1 回渡すだけです。

なお候補 2 の 10.2 秒は QueryTable 固有のものではなく、全列を `xlTextFormat` に
指定したうえでの値です。列の型自動判定を許すと郵便番号側で数値化が起きるため、
速度のために型指定を外すことはできません。

## 3. 出力フェッチ／書戻し方式の全比較 (1,000,000 件 / 各 5 回)

ここまでで「結果の戻し方が支配的」と分かったので、戻し方だけを 6 通り実装して
同じ条件で並べました。方式 9・13・14・15 は**ワーカーが書いたまったく同じ 1 本の
ファイル**を読みます。中身は 1 バイトも違わず、違うのは Excel 側の取り込み経路だけです。
方式 10 はファイルを介さず COM でセルへ直接書き、方式 16 は Excel のプロセスの中で走ります。

起動手段は 9・10・13・14・15 のすべてで `WScript.Shell.Run` に固定しています。
方式 16 だけは起動の意味が違い、`Application.RegisterXLL` の時間です。

### プロバイダーの入手可否

推測で除外した方式はありません。この環境では全部が実際に動きました。

| 必要なもの | 状態 |
|---|---|
| `Microsoft.ACE.OLEDB.12.0` / `16.0` | 64bit 版が登録済み |
| `ADODB.Connection` / `ADODB.Recordset` | 登録済み |
| `DAO.DBEngine.120` / `36` | 登録済み (`ACEDAO.DLL`) |
| Excel-DNA (`ExcelDna.Integration` 1.9.0) | nuget.org から取得してビルド |
| Excel 本体 | 16.0 x64 (ClickToRun) |

ADO・DAO は 64bit の ACE が入っていることが前提です。32bit Office に 64bit ACE、
あるいはその逆の組み合わせでは `Provider が見つかりません` で止まります。
その場合も別方式へ切り替えず、失敗として記録する作りにしてあります。

### 読み取り

**同じファイルを読んでいるのに、経路だけで 10 倍違う。**
`Excel 反映` の列がそのまま順位になっています。1.027 → 6.113 → 7.379 → 10.322 秒。

- **ADO が飛び抜けて速い (1.027 秒)。** `QueryTable` の 10 分の 1 です。
  ACE のテキスト ドライバが行を返し、`CopyFromRecordset` が Excel 内部へ直接流し込む
  経路が、Excel 自身のテキスト パーサより速い。
- **DAO は同じ `CopyFromRecordset` を使って 7.379 秒。** ADO の 7.2 倍かかります。
  ファイルも `schema.ini` も宛先も同一で、違うのはプロバイダー層だけです。
  ADO と DAO を「どちらもレコードセット経由」と一括りにはできません。
- **`QueryTable` が最下位 (10.322 秒)。** 全列を `xlTextFormat` に固定した状態での値です。
  型の自動判定を許すと郵便番号側で数値化が起きるので、速度のために型指定は外せません。
- **`Workbooks.OpenText` は 6.113 秒。** 別ブックとして開いてから範囲ごと複写する 2 段構えで、
  `QueryTable` より速いが Recordset 経由には勝てません。

**XLL がすべてを通して最速 (E2E 0.773 秒)。** 差が出るのは読み書きの両側です。

- Master 読込 0.021 秒 (COM の 0.094 秒)、Input 読込 0.101 秒 (COM の 0.389 秒)。
  **4 倍前後の差**が、同じ「1 回の一括読み」で出ます。
- 出力 0.551 秒 (COM の 0.834 秒)。
- 差の正体はプロセス境界です。方式 10 のワーカーは別プロセスから COM を呼ぶので、
  1,000,000 要素の SAFEARRAY がプロセス間でマーシャリングされます。XLL は Excel 自身の
  プロセスに読み込まれ、C API (XLOPER12) でメモリを直接受け渡すのでそれが要りません。
- 通知が 0.018 秒と小さいのは、同期呼び出しなので通知セルも `Worksheet_Change` も
  使っていないためです。待つ相手がいないところに通知を挟んでも、測るものが増えるだけです。
- 起動 (`RegisterXLL`) の中央値は 0.124 秒で、5 回とも 0.114〜0.147 秒に収まりました。
  初回だけ最初の関数呼び出しで実行時の読み込みが入るぶん、E2E が数十ミリ秒大きく出ます。

### まとめると

同じ 1,000,000 件を同じ規則で変換して同じシートへ入れるのに、**0.773 秒から 10.948 秒まで
14.2 倍の開き**があります。変換そのものはどの方式でも 0.05 秒前後で、順位に何も寄与しません。
効いているのは、

1. **プロセス境界を越えるか** (XLL 対 それ以外)
2. **Excel の内部表現に入るまでに何回テキストを経由するか** (COM/XLL 対 ファイル経由)
3. **ファイル経由なら、どのドライバに読ませるか** (ADO 対 DAO 対 Excel 自身)

の 3 点だけです。

## 4. 計測方法について

- 時刻は `QueryPerformanceCounter` を `Currency` で受けています。VBA の `Timer` は
  `Single` のため、正午過ぎ (約 42,600 秒) では 1 ULP が 3.9 ミリ秒になり、
  0.05 秒の変換区間を測る分解能がありません。
- 終了時刻は `Worksheet_Change` ハンドラの中で最初に打刻します。ハンドラから戻った後に
  打刻すると、画面更新の再開分が処理時間に混ざります。
- ワーカー内訳 (bind / master / input / dict / convert / write) はワーカー側の
  `Stopwatch` の値で、Excel 側の区間とは独立に取っています。両者の合計が処理 E2E に
  一致しないぶんは、プロセス起動・UIA でのハンドオフ・通知の往復です。
