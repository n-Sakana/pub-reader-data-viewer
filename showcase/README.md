# VBA Pixel Bridge — Excel分離アーキテクチャ 技術ショーケース

要件定義 v2 の実装。正本は同じフォルダの 2 文書：

- `VBA Pixel Bridge — Excel分離アーキテクチャ 技術ショーケース 要件定義 v2.md`
- `VBA Pixel Bridge — Excel分離アーキテクチャ 技術ショーケース 要件定義 v2.html`

画面は v3 モック（`PIXEL BRIDGE モック v3.html`）の実寸に合わせてある。
これは reader-data-viewer 本番版の改修ではない。`showcase/` の中で完結する。

## つくりかた（ダブルクリック）

`showcase\ビルド.bat` をダブルクリックする。管理者権限も UAC も要らない。
ExecutionPolicy はこの呼び出しの中だけ `-ExecutionPolicy Bypass` で外すので、
利用者が設定を変える必要もない。

コンソールに 1 / 2 / 4 の選択肢が出る。**疑似ピクセル GUI の「1 セルが受け持つ
設計ピクセル数」**を選ぶと、そのぶんだけをビルドする。

```
   1 ... 1px   仕様どおりの細かさ。盤面 812 x 812 = 659,344 セル
   2 ... 2px   中間。            盤面 406 x 406 = 164,836 セル
   4 ... 4px   いちばん軽い。    盤面 203 x 203 =  41,209 セル
```

- **既定値は置いていない。** 何も入れずに Enter を押しても、知らないうちに 4px が
  選ばれたりはしない。「何も入力されませんでした」と言って選び直させる。
- 選んだ値は成果物の名前（`dist\VBA Pixel Bridge 2px.xlsm`）と画面フッタ
  （`1 セル = 2px`）の両方に出る。開いたあとでも、どれを選んだか分かる。

引数で選ぶこともできる。ダブルクリックしたときは引数が無いので対話メニューへ進む。

```
ビルド.bat 2          … 2px で作る
ビルド.bat 3          … 選べないので何も作らず終わる（exit 1）
```

コマンドから直接叩くときも同じで、`-Unit` は必須：

```powershell
powershell -ExecutionPolicy Bypass -File showcase\build\build_showcase.ps1 -Unit 2
```

## 成果物

| もの | 何か |
|---|---|
| `dist/modPixelBridge_<N>px.bas` | 仕様上の成果物。標準モジュール 1 枚（ANSI / CP932） |
| `dist/VBA Pixel Bridge <N>px.xlsm` | その .bas を取り込み、UIAutomationClient の参照を付けたブック |

参照設定は既定の 4 つ（VBA / Excel / stdole / Office）に **UIAutomationClient を
1 つ足すだけ**。Win32 API / `Declare` / `Shell` / `WScript.Shell` / 外部 helper は
1 つもない。図形（Shape）もフォームコントロールも ActiveX も使わない。画面は
すべてセルの塗りと結合セルで描いてある。

ブックには標準モジュール 1 枚のほかに、`ThisWorkbook` へ数行だけ入れてある。
ポンプの見張り（`PbEnsureArmed`）と、閉じる合図（`PbPrepareClose`）を呼ぶだけで、
判断はすべて .bas 側にある。標準モジュールからはブックのイベントを取れないため。

## 使い方

1. **メモ帳を 2 枚開いておく。**片方に文章を書き、もう片方は空のままにする。
   文章があるほうが「原稿」、空のほうが「清書」になる。アプリはメモ帳を起動も
   終了もしない。開いている窓に UI Automation でつなぐだけ。
2. `dist\VBA Pixel Bridge <N>px.xlsm` を開く。「コンテンツの有効化」を押す。
3. `Auto_Open` が画面を組み、1 秒ごとのポンプが回りはじめる。
4. ミニマップの中を **ドラッグで矩形選択**すると、選んだ窓をその矩形へ移動・
   リサイズする（`TransformPattern.Move` / `Resize`）。`左右 2 分割` /
   `上下 2 分割` は一括配置。
5. 右下の `FE で清書（固まる）` / `BE で清書（固まらない）` が本題。下を参照。
6. 閉じるときはふつうにブックを閉じる。`Auto_Close` が BE を終わらせ、Temp と
   BE 用コピーを消す。

### ショートカット（Application.OnKey）

`Ctrl+Shift+M` 同期の入 / 切 ・ `Ctrl+Shift+F` FE で清書 ・ `Ctrl+Shift+B` BE で清書

アニメーションは常時 1 秒。速さの切替（5 秒 / なし）とそのボタンは廃止した。
1 秒で回らないなら作る意味がない、が owner の判断で、実際 1 秒で回るように
なったので切り替える理由も無い（下の「描画の直し」を参照）。

ボタンはセルで描いてあり、押下は「そのセルが選択されたこと」でポンプが拾う。
ホバーするとハイパーリンクの ScreenTip が説明を出す。

## 本題：同じ重い処理を、FE で回すか BE へ逃がすか

**原稿（メモ帳 A）を 1 文字ずつ清書（メモ帳 B）へ写す。** 1 文字書くたびに、
そこまで書いた分を頭から読み直して原稿と突き合わせる（校正）。だから k 文字目の
コストは k に比例し、全体は文字数の 2 乗で効く。速くする工夫は入れない。

原稿が短いと一瞬で終わって差が見えないので、「原稿を何周読み直すか」で総量を
揃える。周回数は確認ダイアログにも画面にも出すので、水増しは隠していない。
総量そのものは実行時に端末の速さを 0.1 秒測って「FE で約 15 秒」になるよう選ぶ
（開発機で決め打ちした固定回数は、非力なノートで 212 秒かかった。実測）。

役割は並び順ではなく**中身**で決める。文章があるほうが原稿、空のほうが清書。
**清書側が空でなければ実行しない。** 清書側は必ず上書きするので、利用者の
書きかけを消さないための歯止め。両方に文章があるときも実行しない。

開発機（2,904 文字 × 校正 71 周）と本番ノート（909 文字 × 校正 375 周）で、実測：

| 実行先 | 開発機 | 本番ノート | FE の応答 | 清書の出かた |
|---|---|---|---|---|
| **FE**（この Excel の中） | 10.3 秒・描画 2 回 | 14.7 秒・描画 1 回 | **応答なし**（実測 Responding=False） | 最後に一度だけ全文 |
| **BE**（非表示の別プロセス） | 14.3 秒・描画 15 回 | 69.8 秒・描画 68 回 | 動き続ける（毎秒 1 ティック） | 0 → 94 → 214 → … → 全文と伸びる |

FE 側は校正の輪の中に `DoEvents` を 1 つも入れていない。演出で止めているのでは
なく、同期実行の結果として本当に止まる。BE 側が遅いのは `DoEvents` と進捗の
書き出しが入る分に加え、不可視のバックグラウンド プロセスは OS に実行効率を
絞られるため（このノートで顕著。同じ総量で約 4.7 倍）。それでも**清書が伸びて
いくこと自体が「FE が生きている」証拠になっている**。BE が計算し、FE の 1 秒
ポンプがその途中経過を読んでメモ帳へ書く。ポンプが止まれば清書も止まる。

### 逃がすだけでは足りなかった（この実装でいちばん効いた修正）

最初の実装では、BE へ逃がしても **FE は同じように固まった**。原因は FE の仕事では
ない。FE の 1 ティックの中にある `ScanWindows`（UI Automation の列挙）が、計算中の
BE を待って返らなかった。実測：ティックの `t:sel` から `t:scan` までが 15.6 秒で、
BE の処理時間とぴたり一致した。

UIA の列挙は端から端まで全部のトップレベル窓に触りにいく。その中に「メッセージを
一切処理しないプロセス」が一つでもあると、そこで止まる。不可視でも窓は窓で、
そこに自分の BE がいた。**重い処理を別プロセスへ逃がすだけでは足りず、逃がした先が
応答し続けないと FE が巻き添えで固まる。**

直し方は BE のループに `DoEvents` を 1 つ入れるだけ。

## ポンプは XLToolRack の JobPump に合わせてある

1 秒ごとの `Application.OnTime` の張り方・止め方・見張りは、`C:\repos\pub\xltoolrack`
の `src/addin/JobPump.bas` と同じ形にしてある。守るのは 1 つだけ：

- **予約は常に 1 本。** `m_armed` が真なら二重に張らない
- ティックは入口で `m_armed` を False に戻し（この予約は消費された）、本体の最後に
  もう 1 本だけ張る。**止めたいときは張らないだけ**でいい
- 見張り（`PbEnsureArmed`）はブック自身のイベントから呼ばれ、予約の時刻を 5 秒
  過ぎてもティックが来ていなければ張り直す。5 秒の猶予は、Excel がセル編集中や
  ダイアログ表示中に OnTime を後回しにするのを故障と取り違えないため

一度この不変条件を破って「ダイアログを閉じた直後にもう 1 本張る」を足したところ、
予約が同時に 2 本生きる状態ができ、閉じるときに取り消しきれなくなった。増築は
撤回して実績のある形へ戻してある。

## 要件 v2 §10「実装時に判断する事項」への答え（すべて実測）

| 判断事項 | 実測 | 採った答え |
|---|---|---|
| 0.5 秒ポーリングの実現方法 | `OnTime Now + 0.5s` は**即時発火**（8 tick が 0.016 秒）。`+1.5s` は 1.0 / 2.0 秒に丸まる | **1 秒**（§10 が認める「1 秒に戻す判断」）。XLToolRack の JobPump も 1 秒 |
| 重い処理の内容と、短すぎるときの調整 | 代入だけだと 10,000 セルで約 1.05 秒。短すぎて FE/BE の差が見えない | メモ帳 2 枚の「原稿 → 清書」に差し替え。総量は**実行時に端末の速さを 0.1 秒測って** FE 約 15 秒になる周回数を選ぶ（開発機で決めた固定回数は、非力なノートで 212 秒かかった） |
| 疑似ピクセルのセル寸法 | 行高・列幅は表示 DPI の 1 デバイスピクセルに丸められる。開発機は 1 デバイスピクセル = 0.5pt、このノートは 0.6pt（125%） | 起動時に実測。ねらいは「1 デザイン px = 0.75pt」だが、**その寸法で盤面が画面に入らない端末では、入る最大の整数デバイス px に切り下げる**。1080p / 125% では 1px / 2px / 4px とも 1 セル = 1 / 2 / 4 デバイス px（盤面 812 デバイス px）になる |

| UIAutomationClient の早期バインディング（tagPOINT） | `ElementFromPoint` は POINT を **ByVal** で取り、VBA は UDT を ByVal で渡せない。**コンパイル**エラーなので実行時には捕まえられない | 早期バインディング（参照設定）必須。点→要素は UIA の矩形ヒットテストで同義に実装 |
| DADS トークンの適用範囲 | — | 色・角丸・4px グリッド・Noto Sans JP を全面に適用。等幅は Noto Sans Mono、無ければ Consolas |

## 実機で測ってわかったこと（設計に効いた順）

1. **`ScreenUpdating` の False → True は、変えた量に関係なくビューポート全体を
   無効化する。その再描画の値段は盤面の複雑さ（色の切り替わり数）で決まる。**
   実盤面の 1px でトグル 1 回 2.4 秒（このノート）。逆に、True のまま少しだけ
   書けば汚した矩形しか描き直さず、同じ盤で直書き 1016ms / トグル 1711ms、
   素の 812×812（65 万セル）ならどちらも 1000ms（probe 実測）。**だから毎秒の
   ティックはトグルせず直書きし、Hold / Release は初期構築・後始末・FE 清書
   だけにする。この 1 点で 1px の 1 秒アニメが成立した**（旧実装は毎ティック
   トグルしていて、1px は 3.4 秒 / ティックまで落ちていた）。
2. **自分の窓の UIA 要素を作ると、以後そのティックのセル書き込みが 1 回
   130ms 級になる。** `ElementFromHandle(自分の hwnd)`（旧 実装は毎スキャン）と、
   フォーカスが Excel 上にあるときの `GetFocusedElement`（毎ティック）が該当。
   Excel 自身の UIA プロバイダがプロセスの中で動き出すため。probe では同じ盤・
   同じ UIA クライアントでも、自分の窓に触らない限り 1 write 5ms のまま。
   → 自分の矩形は `Application.Left/Top/Width/Height` × 実測 px/pt 比から作り、
   フォーカスは**メモ帳側の文書要素（外部プロセス）に `HasKeyboardFocus` を
   尋ねる**。自分の窓に UIA で触るのは起動時の pid 取得 1 回だけ（実測で無害）。
3. **背面の Excel が OnTime の中で出す `MsgBox` は、窓が作られない「見えない
   モーダル」になる。** OK が届くまでポンプごと止まり（実測 90 秒）、fe.json が
   止まるので BE が置き去り判定で自分から終わる、まで連鎖した。
   `vbMsgBoxSetForeground` でも `AppActivate` でも直らない。→ 完了ダイアログは
   その場で出さず、**利用者の次の操作（セル選択・ウィンドウ復帰）まで持ち越す**。
4. **このメモ帳（11.2606 / Windows 26200）は、UIA の TransformPattern を
   どの要素にも公開しない。**（窓も子孫も IsTransformPatternAvailable=False。
   XLMAIN も同じ。）.NET 管理 UIA だけが旧プロキシで合成して動かせるが、VBA の
   ネイティブ COM UIA からは動かせない。→ 整列は Excel（自分の窓、Application
   座標）だけ動かし、メモ帳が動かせないことを画面に正直に出す。
5. **UIA のパターンを `As Object` で受けてはいけない。** パターンは IUnknown 系で
   IDispatch を持たず、`Set` の時点で失敗して Nothing 扱いになる（整列が「1 窓
   しか動かない」ように見えた）。`IUIAutomationTransformPattern` 等の型で受ける。
6. **メモ帳の ValuePattern は改行を CR に正規化した文字列を返す**（CRLF を
   SetValue しても読み返すと CR）。控えを CRLF で持つと毎回「相手が変わった」と
   誤読する。控えは LF 正規形に統一する。
7. **セルの控えは「書いた値」ではなく「書いた結果セルが返す値」で持つ。**
   Excel は代入で先頭の `'` を落とす・数字や日付に化かすなど値を黙って直す。
   意図した値で控えると、次のティックが「セルが編集された」と誤読し、化けた
   文字列をメモ帳へ書き戻す（利用者の文字が勝手に変わる）。入力セルには
   `NumberFormat="@"` も併せて敷く。
8. **同期スロットは窓（hwnd）に貼り付ける。** `FindAll` の並びは Z 順で、
   利用者のクリック 1 つで入れ替わる。並び順でスロットを割ると、入れ替わった
   先へ前の窓の本文を書き戻して**利用者の文章を消す**。hwnd で対応を取り、
   結び直した直後の 1 回は必ずメモ帳 → セルの向きで揃える。
9. **表示設定の切り替えは、列幅を詰める前にやる。**
   グリッド線と見出しの切り替えは、そのシートの列と行を全部並べ直す。列幅が既定の
   うちは一瞬だが、812 列を 0.08 まで詰めたあと（1px）にやると **276 秒**かかった。
   シートを作った直後・幅を詰める前に同じ 3 行を実行すれば 0.1 秒。4px では気づけない。
10. **応答しないプロセスが 1 つあると、UIA の列挙はそこで止まる。**
   止めていたのが自分の BE だった（上の §）。忙しくする側にも `DoEvents` を入れる。
   ただし毎文字は過剰で、DoEvents 自体が仕事の 5 倍かかる（実測 1 回 1.6ms）。
   64 文字に 1 回で応答は保てる。
11. **`Input$(LOF(f), f)` で日本語のファイルは読めない。**
   これは「LOF バイト分の**文字**」を要求する読み方で、中身が ASCII のうちは動く
   （バイト数＝文字数）。CP932 の日本語は 1 文字 2 バイトなので必ずファイル末尾を
   越え、読み取り全体が落ちる。実測：原稿を渡した BE が毎回「原稿が読めません」を
   返した。`Open For Binary` + `Get` + `StrConv(b, vbUnicode)` で読む。
12. **窓の大きさは `UsableWidth` / `UsableHeight` に合わせてはいけない。**
   `UsableWidth` は縦スクロールバーを含み、`UsableHeight` はシート見出しと横
   スクロールバーを含む。合わせると設計の右端と下端が窓の外へ出る（実測：右下の
   ボタンが切れ、横スクロールバーが出た）。`ActiveWindow.VisibleRange` の列数・
   行数で、必要数より 1 つ多く見えるまで広げる。
13. **保存したブックに 1px グリッドのシートを残すと、開いた瞬間に固まる。**
   その場で作れば行高 812 行が 2 ms、列幅が 0 ms。毎回作り直し、終了時に消す。
14. **強制終了された FE は `fe.json` を残す。**
   BE が「ファイルが無い＝FE が消えた」だけを見ていると、残ったファイルを見て永遠に
   回り続ける（実測：FE を kill したら BE だけが残った）。中身が更新されているかで
   見る。ただし待つ長さは長めに（90 秒）。FE は正常でも黙る時間がある — 起動直後の
   最初の再描画、そして「FE で清書」を選んだときは仕様どおり十数秒完全に固まる。
   逆に BE が自分から終わったら（`bye`）、FE は次のジョブで BE を起こし直す。
15. **ActiveX コントロールは現行 Office の既定で挿入できない**（1004）。テキスト入力は結合セル。
16. **小さいピッチでは文字の実描画が名目ポイントより広くなり、中央揃えの札が
   両端から欠ける**（実測：セル 3 デバイス px で「左右 2 分割」の左右が消えた）。
   ボタンの札は `ShrinkToFit` で幅に収まるまで縮めさせる。

## 開発中の落とし穴（計測器が対象を壊していた）

`Application.OnTime` が BE の中で一度も発火しない、という現象を長く追った。結論は
**プラットフォームの制約ではなく、調べ方が壊していた**。

BE を覗くためのスクリプト（`verify/probe/inspect_be.ps1`）が、その Excel の VBE で
「VBAProject のコンパイル」を実行していた。自動化（`CreateObject`）で起こした Excel の
VBE を触ると、そのインスタンスは壊れる。以後 `OnTime` は `Err.Number = 0` のまま沈黙し、
常駐ループも 1 周で無応答になる。`Application.Run` は通るので「COM は生きているのに
OnTime だけ死ぬ」という紛らわしい見え方をする。しかも `FindControl(1,578)` は
`Enabled = False`（＝押せない）で返ることがあり、その場合 `Execute()` は何も検査して
いない。壊すだけで、確かめない。

VBE に触らない `verify/probe/probe_be_loop.ps1` で同じブックを走らせると、bootstrap は
8 ms で返り、常駐ループは `idle → running → done → bye` まで通ってプロセスが自分から
終わる。再現手順は `probe_be_loop.ps1 -Compile`。

## 仕様との差分（正直に）

| 仕様 | 実装 | 理由 |
|---|---|---|
| ポーリング 0.5 秒 | 1 秒 | 上表のとおり。§10 が想定している判断 |
| §6 の重い処理「100 行×100 列に代入」 | メモ帳 2 枚の「原稿 → 清書」 | 代入だけでは 1 秒で終わり、FE/BE の差が体感できない。要件定義も更新済み |

| `PB_UNIT` | 盤面 | 1 セルの実寸 | 起動（画面が出るまで） | 1 秒アニメ | 実画面確認 |
|---|---|---|---|---|---|
| 1px | 812×812 = 659,344 セル | 1 デバイス px | 約 3 秒 | **1.01～1.08 秒を保つ** | 済（本番ノート実機） |

## 未検証・積み残し

- **開発機で見えていた「FE プロセスが閉じたあとも残る」は、本番ノートの一連の
  検証（10 回以上の開閉）では一度も再現しなかった。** どの回も ✕ 相当の
  WM_CLOSE から数秒でプロセスまで消えている。開発機側の条件は切り分け未了のまま。
- ホバーツールチップ（ScreenTip）の見た目は自動では確かめられていない。
- 3 窓以上のメモ帳、1 時間以上の連続稼働は未確認。
- 完了ダイアログは「次の操作」で出す方式なので、完了後に一度も Excel を
  触らなければ出ない（完了自体は盤面に出ている）。同じセルをもう一度クリック
  しただけでは選択が変わらず出ない、という端も理屈上ある。
- BE の所要が FE の 4～5 倍（このノート）。不可視バックグラウンド プロセスへの
  OS の実行効率制限が疑わしいが、Win32 なしでは優先度を変えられないので放置。
  「FE が生き続ける」という主題には影響しない。
