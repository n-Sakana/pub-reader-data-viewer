# VBA Pixel Bridge — Excel分離アーキテクチャ 技術ショーケース 要件定義 v2

reader-data-viewer の本番アーキテクチャを流用した検証／デモ用モック。
「Excel VBA だけでどこまでできるか」の技術ショーケースを兼ねる。
v1 からの変更点は各項の末尾に `※v1 からの変更` として記す。

---

## 1. 目的

- 最初の検証／デモ用モック
- 技術ショーケース（VBA のみでの外部アプリ連携・非同期化・GUI 描画）

## 2. 制約

- VBA のみ。C# の埋め込みなし、処理を外部プロセスに投げない
- Win32 API なし、Shell なし
- 成果物は .bas 1 枚（標準モジュールのみ）
- 参照設定は UIAutomationClient のみ
- ユーザーのディレクトリを汚さない（一時ファイルは Temp、Excel 終了時に削除）

## 3. アーキテクチャ

- FE：疑似ピクセル GUI の Excel（ユーザーが操作する側）
- BE：別プロセスの非表示 Excel（重い処理を担当）
- FE⇔BE 通信：Temp フォルダの JSON ファイル。Excel 終了時に削除

### 3.1 BE の起動と実行（実装上の要点）

- BE の起動は `CreateObject("Excel.Application")` で可。COM のみで Win32 API も Shell も不要。`.Visible = False` で非表示
- **FE→BE の呼び出しは即 return 必須**。`beApp.Run "BeMain"` を同期で呼ぶと処理完了まで FE がブロックされ、非同期化の意味がなくなる。BE 側の入口で `Application.OnTime` を仕込んで即座に戻し、実処理は BE 自身のタイマーで回す
- **BE 用ブックの置き場所**：プログラムから開いたブックは信頼できる場所以外だとマクロが黙って無効化される。したがって BE 用ブックは元ファイルと同じ（信頼済みの）フォルダへコピーし、`%TEMP%` は JSON のやりとりだけに使う
- `Auto_Open` は `Workbooks.Open` では走らないため `wb.RunAutoMacros xlAutoOpen` で明示的に起動する

※v1 からの変更：BE 起動可否とマクロ信頼の制約を明記

## 4. 画面構成

- **812 × 812 の正方形。スクロールなしで収まる**
- 想定：1920×1080 の左半分（960×1040）に Excel を置き、右半分にメモ帳を並べて使う。Excel の枠・リボンを除いたクライアント領域に収まるサイズ
- 構成：ヘッダー帯 ＋ **大きく 2 分割** ＋ フッター
  - 上：**UI Automation 連携**（メモ帳との双方向同期 ＋ ウィンドウ制御 ＋ 要素情報）
  - 下：**フロントエンド・バックエンド分離**
- Excel のシート枠・リボンは見せない（画面だけ）
- 疑似ピクセル描画の粒度は **ビルド時に 1px / 2px / 4px から利用者が選ぶ**。設計座標は 812×812 px のまま、1 デザイン px = 0.75pt（列幅 0.08 / 行高 0.75pt 相当）も変わらない。変わるのは「1 セルが何デザイン px を受け持つか」だけ。
  - 既定値は置かない。選ばずにビルドはできない
  - 選んだ値は成果物のファイル名（`VBA Pixel Bridge 2px.xlsm` 等）と画面フッタ（`1 セル = 2px`）の両方に出す
  - セル境界の可視化は 3px 以上のときのみ描く（1px ではグリッド線が引けないため）

※v1 からの変更：2×2 のカードグリッド → 上下 2 分割。Excel の枠は非表示
※v2 内の変更：1 セル 1px 固定 → 1 / 2 / 4px の選択制（この端末では 1px は描画は通るが 1 秒アニメに追いつかない。README の実測を参照）

### ヘッダー帯

- アプリ名
- 起動からの経過時間
- 同期ステータスのランプ ＋ ポーリング回数
- ダーク／ライト切替

### 上段：UI Automation 連携

**メモ帳 ⇄ Excel 同期パネル（左）**

- ある程度の大きさのテキストボックスで**フリー同期**。文字種別判定・1 文字制限・送信ボタンは廃止
- メモ帳が 2 窓あるので**テキストボックスも 2 つ**。窓ごとに独立して同期（複数タブも同じ扱い）
- フォーカス中の窓に対応するテキストボックスは枠を強調
- 同期の開始／停止トグル
- 状態表示：`SetValue 待ち` / 取得時刻

※v1 からの変更：判定カテゴリ表示（「これは数字です」）を全面廃止。読み取りと書き込みを分離せず同期に統合

**ミニマップカード（右）**

- 実画面を縮小し、各ウィンドウの位置をリアルタイム追従。従来より大きく取る
- **整列ボタン 2 つ（左右 2 分割 / 上下 2 分割）はミニマップカードのツールバー内に置く**。ミニマップの操作であることを配置で示す
- クリックでインスペクト（ElementFromPoint）。クリック位置から画面座標を逆算して `CLICK PT x, y` を表示
- クリックによるウィンドウ移動は行わない

※v1 からの変更：整列ボタンをミニマップカードのツールバーへ。カード外に離して置かない

**要素情報（下段左右、同型）**

- 左：`GetFocusedElement`（フォーカス中）— Name / ControlType / ClassName / AutomationId / ProcessId / Value(Len)
- 右：`ElementFromPoint`（クリックした点）— アプリ名 / ウィンドウ名 / ClassName / ProcessId / Rect / CanMove
- **両パネルは同じ 6 行・同じ行高・キー列 92px の 1 列表**にして文字の詰まり方を揃える
- 位置の対応：フォーカス情報は同期パネルの下、ElementFromPoint はミニマップの下

※v1 からの変更：左右の位置関係を入れ替え。密度を揃えた。Rect は `x, y · w×h` の収まる表記に。取得できて意味のある項目（CanMove / Value）を追加

### 下段：フロントエンド・バックエンド分離

- FE ボックス（この Excel / pid・状態・注記）
- BE ボックス（非表示の Excel / pid・状態・注記）
- **進捗の可視化は 10×10 のマトリクス**。1 マス = 100 セル。実際の代入がどちら側で進んでいるかがそのまま見える。意味のない波形アニメーションは廃止
- 中央に `%TEMP%\pixelbridge\` のレーン
  - `command.json →`（FE→BE）
  - `← progress.json`（BE→FE）
  - 各レーンにパケットの流れと **実際の payload** を表示（例 `{"pct":42,"cells":4200,"ts":"21:27:06"}`）
- ボタン 2 つを横並び：左＝FE で実行（固まる）／右＝BE で実行（固まらない）
- プログレスバー ＋ 経過秒 ＋ 件数
- 完了時に所要時間と件数をダイアログ表示

※v1 からの変更：FE/BE の稼働状況とファイルのやりとりを可視化。BE のダミー波形は削除

### フッター

- キーボードショートカット一覧
- 1 セルのサイズ表記 / DADS 準拠表記
- **トースト通知は廃止**（状態の変化そのもので示す）

※v1 からの変更：右下からのトーストを削除

### 共通

- 各ボタンにホバーツールチップ（ハイパーリンクの ScreenTip）
- 各カードの隅に使用技術名を小さく表示（UIAutomationClient / TransformPattern / Application.OnTime 等）

## 5. 同期仕様

- UI Automation でメモ帳をポーリング。**間隔 0.5 秒**
- 取得した本文はそのままテキストボックスへ反映。文字種別の判定はしない
- テキストボックス側が編集されていれば `ValuePattern.SetValue` で書き戻し、差分がなければ `GetValue` のみ
- 複数ウィンドウ・複数タブに対応。窓ごとに独立して同期
- メモ帳は**起動している前提**。アプリ側から起動はしない

※v1 からの変更：1 秒 → 0.5 秒。判定仕様を削除。1 文字制限を撤廃

## 6. 重い処理

- 明示ボタンで実行。常時は走らせない
- 実行前に確認ダイアログ
  > 新しいブックを開いてこの処理をします。ローカルには保存しません。よろしいですか
- 内容：**メモ帳 2 枚を使う「原稿 → 清書」**。文章が入っているほうを原稿、空のほうを清書として、原稿を 1 文字ずつ清書へ写す。1 文字書くたびに、そこまで書いた分を頭から読み直して原稿と突き合わせる（校正）。だから k 文字目のコストは k に比例し、全体は文字数の 2 乗で効く
  - 役割は並び順ではなく中身で決める。清書側が空でなければ実行しない（利用者の書きかけを上書きしないため）
  - 原稿が短いと一瞬で終わるので、「原稿を何周読み直すか」で総量を揃える。周回数は確認ダイアログと画面に出す
- 高速化の工夫は入れない（意図的に重くする）
- FE 実行時：フロントエンドが固まる（対比のデモ。応答なし表示）
- BE 実行時：非表示の別プロセス Excel が担当。FE は固まらない
- BE が進捗を JSON に、清書の途中経過をテキストファイルに書き、FE が 1 秒ごとに読んで進捗盤・経過秒を更新し、**清書をメモ帳へ書き足す**
- BE 実行では清書が少しずつ伸びる。FE 実行では画面が固まったまま伸びず、最後に一度だけ出る。これが FE/BE 分離のいちばん分かりやすい見え方
- 完了時に所要時間と件数をダイアログ表示
- 実測で短すぎる場合は、書式設定を併せて行い所要時間を調整する

## 7. ウィンドウ整列

- UIA `TransformPattern.Move / Resize`、`WindowPattern.SetWindowVisualState`
- パターン：左右 2 分割 / 上下 2 分割
- Excel とメモ帳を並べる。メモ帳が複数なら片側を等分
- 画面サイズは UIA ルート要素の矩形から取得
- 最大化されたウィンドウは `CanMove` が False になるため、先に通常表示へ戻す
- Excel 自身も UIA 要素として扱い、単位系を UIA に統一する（DPI 問題の回避）

## 8. ショーケース要素（全 10）

1. UI Automation による外部アプリ連携
2. メモ帳との双方向フリー同期（読み取りと書き込みの統合、複数窓対応）
3. 疑似ピクセル（1px セル）によるフロントエンド描画
4. FE/BE 分離による固まらないアーキテクチャ
5. FE/BE の稼働状況と JSON のやりとりの可視化
6. ウィンドウのミニマップ（リアルタイム追従）
7. ウィンドウ整列（Win32 なし）
8. インスペクション（ElementFromPoint / GetFocusedElement / クリック座標の逆算）
9. ホバーツールチップ（ハイパーリンクの ScreenTip）
10. キーボードショートカット（Application.OnKey）＋ ダーク／ライト切替

※v1 からの変更：文字種別判定・疑似ピクセルアニメ（トースト/スピナー）を外し、同期と FE/BE 可視化を主役に

## 9. 技術上の制約と回避策

| やりたいこと | 素の可否 | 採る方法 |
|---|---|---|
| マウスカーソル座標の取得 | 不可（Win32 GetCursorPos が必要） | ミニマップのクリック位置から逆算 |
| ドラッグでウィンドウを動かす | 不可（マウスイベントが取れない） | 行わない。整列ボタンのみ |
| メモ帳の起動 | Shell / WScript.Shell は制約違反。WMI `Win32_Process.Create` なら COM のみで可、`FollowHyperlink` は警告ダイアログが挟まる | 行わない。**起動済みを前提**にする |
| 非表示 Excel（BE）の起動 | 可（`CreateObject("Excel.Application")`、COM のみ） | 採用。ただし呼び出しは即 return、BE ブックは信頼済みフォルダに置く |
| Windows のトースト通知 | 不可（Win32 / WinRT が必要） | 採用しない（シート内トーストも廃止） |
| HTML ダッシュボードをブラウザ表示 | 可（Temp + FollowHyperlink） | 採用しない（疑似ピクセル GUI が霞むため） |
| data: URI でブラウザ表示 | 不可（主要ブラウザがブロック） | — |
| 0.5 秒ポーリング | `Application.OnTime` は秒未満が不安定、Sleep は禁止 | 0.5 秒を目標値とし、OnTime の実挙動を測って詰める（下記 10 参照） |

## 10. 実装時に判断する事項

- **0.5 秒ポーリングの実現方法**。`Application.OnTime` の最小粒度は 1 秒相当なので、0.5 秒を出すには 1 秒 OnTime + 中間の追加スケジュール等の工夫が必要。実測して 1 秒に戻す判断も含める
- 重い処理の所要時間が短すぎる場合の調整方法（書式設定の併用）
- 疑似ピクセルのセルサイズ確定（1 デザイン px に相当する列幅・行高の実値）と、1 / 2 / 4px の選択をどうビルドへ渡すか
- BE 用ブックの配置と信頼できる場所の扱い（デモ機の設定手順）
- UIAutomationClient の早期バインディング要否（tagPOINT の扱い）
- デジタル庁デザインシステムのトークン適用範囲（下記 11）

## 11. デザイン

- デジタル庁デザインシステム（DADS β v2 系）準拠
- キーカラー Blue-900 `#0017C1`（ダーク時は Blue-400 `#7096F8` / 帯は Blue-1100 `#000071`）
- ニュートラルは Solid Gray（境界 `#CCCCCC`、副文字 `#767676`、文字 `#1A1A1A`）
- 書体：和文 Noto Sans JP、数値・API 名は Noto Sans Mono
- 角丸 8px、余白は 4px グリッド
- ライトを主、ダークは切替で提供（DADS はライト前提のため、ダークは自前で反転設計）
