# 計測結果 — 3 方式の merge-select

計測環境: Windows 11 Home 26200 / Excel 16.0 (64bit, build 20228) / .NET Framework 4.8 の
`csc` / Windows PowerShell 5.1 (64bit) / Core i7-13620H / 16 GB / ローカル NVMe。

データ: `build/gen_data.ps1` が生成する合成 CSV 3 本。各 1,000,000 データ行 × 10 列、
合計 241 MB。3 方式は**同じファイルの同じバイト**を読みます。

各方式 8 回ずつ、計 24 回。**24 回すべて検算 OK。**

## 1. 何を 1 回として測ったか

**merge-select** = 番号が確定した瞬間から、画面にその 1 件が出るまで。

| # | 工程 | 中身 |
|---|---|---|
| 1 | 表A 読込・索引 | ファイル全体を読む → 行オフセット走査 → 番号1 のハッシュ索引を作る |
| 2 | 表B 読込・索引 | 同上 (番号1) |
| 3 | 表C 読込・索引 | 同上 (番号2) |
| 4 | A-B 結合 | 表B の**全 1,000,000 行**について番号1 で表A を引き、相手行を確定する |
| 5 | B-C 結合 | 表B の**全 1,000,000 行**について番号2 で表C を引き、相手行を確定し、検算値を畳み込む |
| 6 | 番号1 検索 | 統合済みテーブルから 1 件取り出し、30 項目を文字列化する |
| 7 | 画面表示 | その 1 件を表示先へ書き、往復確認が返るまで |

**キャッシュはしません。** 引き金が引かれるたびに 1〜7 を最初からやり直します。前回の
統合結果も、読み込んだファイルも、索引も持ち越しません。「2 回目だから速い」を作らないのが
この計測の目的です。

計測外なのは 2 つだけです。

- **検知遅延** — ポーリングが番号を確定するまでの時間。参考値として別に記録します。
- **起動時間** — C# のコンパイル、Excel の起動、ブックの表示。監視開始より前に終わらせます。

### 読み取り

**方式差は 5.3 倍。** 併用 0.59 秒に対して VBA 単独 3.14 秒。C# 単独は 0.66 秒。

**効いているのは読み込みと結合だけです。** どの方式でも合計の 99% 以上がここに集まります。
検索は 0.1 ms 未満、表示はいちばん重い C# 単独でも 34 ms で、順位に寄与しません。

**同じアルゴリズムで VBA は C# の 4.6〜5.1 倍。** 読込は 4.6〜5.8 倍、結合は 4.5〜5.9 倍。
配列添字とバイト比較の繰り返しコストがそのまま出ています。VBA が遅いのは「書き方が悪いから」
ではありません — 後述のとおり、この両者は同じ手順を同じ順序で実行しています。

**表示だけは順位が逆になります。**

| 方式 | 表示 | 経路 |
|---|---:|---|
| VBA 単独 | 1.9 ms | 同じプロセスのシートへ `Range.Value2` に配列を 1 回 |
| C# 単独 | 34.1 ms | `Invoke` で UI スレッドへ渡し、ListView を更新して `Refresh()` |

30 項目という小さなデータでも、**プロセス境界と UI フレームワークの差は 18 倍**あります。
`benchmarks/excel-background-bench` が 1,000,000 行で見つけた「効くのは結果の戻し方」は、
1 行でも同じ向きに効きます。ただし絶対値は 34 ms で、3 秒の処理の前では誤差です。

**併用の「その他」16.3 ms** は監視スレッド (MTA) から実行スレッド (STA) へ仕事を渡す
待ち時間です。5 ms 間隔で拾いに行く実装なので、平均 2.5 ms + COM 越しの状態表示更新が
ここに入ります。C# 単独では同じスレッドで続けて処理するため 2.4 ms しかありません。

**C# 単独と併用の結合工程に 10〜13% の差**があります (160.4/171.9 対 139.6/151.3)。
両者は文字通り同じソースから作られた同じコードで、違いは実行スレッドの種別 (MTA / STA) と
同居プロセスの有無だけです。原因は特定できていないため、**併用のほうが結合が速い、とは
結論しません**。合計の差 70 ms のうち説明できるのは表示の 24 ms です。

### 検知遅延 (参考値・計測範囲外)

3 方式とも 143〜151 ms。内訳は「安定待ち 120 ms + ポーリング間隔 40 ms の粒度」で、
実装差ではなく設定値そのものです。8 桁を 15 ms 間隔で打ち込む試験では、確定までに
4 回のポーリングが走っていました。

### 検知規則の確認

カードリーダーを模して `WM_CHAR` を 1 文字ずつ送り、発火回数を数えました
(C# 単独方式、ポーリング 40 ms / 安定 120 ms / 8 桁)。

| 与えた入力 | 期待 | 実測 |
|---|---|---|
| 10 桁を 15 ms 間隔で 1 文字ずつ | 発火しない (8 桁ではない) | **0 回** |
| 8 桁を 15 ms 間隔で 1 文字ずつ | 1 回だけ | **1 回** (4 ポーリングで確定) |
| そのまま放置 (同じ値が欄に残る) | 発火しない | **0 回** |
| 欄を空にして同じ 8 桁をもう一度 | 発火する | **1 回** |
| 8 桁を一括で貼り付け | 1 回だけ | **1 回** |

1 行目が要点です。**8 文字目が入った瞬間には発火しません。** 形式と長さだけで判定すると
10 桁入力の先頭 8 桁で誤発火しますが、120 ms の安定待ちがあるため、続く 9・10 文字目で
候補が変わり確定に至りません。逆に、リーダーが遅くて 8 文字目の後に 120 ms 以上空くと
発火します。この待ち時間は「取りこぼさない最短」と「誤発火しない最長」の間の設定値で、
`RDV_STABLE_MS` / `RdvWatch.StableMs` を変えれば動かせます。

## 3. 3 方式が同じ仕事をしている証拠

方式間の差を「方式の差」と言うためには、中身が同じでなければ意味がありません。
毎回の実行が次の 3 つを報告し、24 回すべてで一致しました。

| 検証項目 | 値 | 意味 |
|---|---|---|
| 結合チェックサム | `658725490` | 表B の**ファイル順**で全行の相手行番号を畳み込んだ値 |
| プローブ数 | `3,639,849` | 3 本の索引を作るときの線形探査の総回数 |
| 突合数 | `1,000,000` / `1,000,000` | A-B と B-C のそれぞれで相手が見つかった行数 |

チェックサムは **`build/gen_data.ps1` が、CSV を書きながら独立に計算したもの**
(`data/expected.txt`) と突き合わせています。読む側の実装がどうであれ、
全 1,000,000 行を正しく結合していなければこの値になりません。

プローブ数の一致はさらに強い条件です。ハッシュ関数・表の大きさ・探査順序・挿入順序の
どれか 1 つでも違えば別の値になります。VBA と C# が同じ数字を出しているということは、
**同じ表を同じ順序で作り、同じ場所で衝突している**ということです。

具体的に揃えてあるもの:

- 入力は同じ 3 ファイル。方式ごとにデータを作り直したりしません。
- 索引は自前のオープンアドレス法ハッシュ表。容量は「行数の 2 倍以上で最小の 2 冪」。
- ハッシュは 8 バイトのキーに対する多項式ハッシュ (`h = h*131 + byte`、各段で 21 bit へ
  マスク、最後に xor-shift)。VBA では 3 か所へ展開してありますが、
  `build/build_workbooks.ps1` が `modRdvSpec.RdvHashBytes` と 1 文字ずつ比較して、
  ずれていればビルドを止めます。
- 行は文字列にしません。1 行は 2 個のバイトオフセット、キーは既知位置の 8 バイトです。
  文字列になるのは**表示する 1 件の 30 項目だけ**です。
- 計測の境界、検知規則 (8 桁・安定 120 ms・連続重複の抑止)、画面の項目と配置は共通です。

## 4. 実測して分かったこと

推測ではなく、この環境で実際に起きたことだけを書きます。

### VBA には 100 万件で使える辞書が無い

`Scripting.Dictionary` に 1,000,000 件の 8 文字キーを入れて引いた結果:

| 操作 | Scripting.Dictionary | 自前ハッシュ表 | 比 |
|---|---:|---:|---:|
| 1,000,000 件 挿入 | 28.2 秒 | 0.19 秒 | 148 倍 |
| 1,000,000 件 参照 | 29.6 秒 | 0.44 秒 | 67 倍 |

1 操作あたり約 30 マイクロ秒。merge-select 1 回には索引構築 3,000,000 回と
参照 2,000,000 回が要るので、`Scripting.Dictionary` のままなら 1 回 150 秒です。
**VBA 側のハッシュ表が手書きなのは、凝りたかったからではなく、既製品では終わらないから**です。

### `Split` は 80 MB の文字列で落ちる

`Split(text, vbLf)` に 79,000,072 バイト (= 79,000,072 文字) を渡すと、
実行時エラー 5 「プロシージャの呼び出し、または引数が不正です」で失敗します。
1,000,000 本の行文字列は作れません。行をオフセットで扱う設計はこの制約から来ています。

なお、ファイル読み込みと行走査そのものは VBA でも速く、1 表あたり
読み込み 0.035 秒 / `StrConv` 0.12 秒 / 行走査 0.14 秒 / キー取り出し 0.11 秒です。
遅いのは 100 万回まわる索引と結合のループのほうです。

### Excel の UI スレッドから UIA で最上位ウィンドウを触ると固まる

VBA から次を呼ぶと**戻ってきません** (CPU は 0%、つまり待ち)。

```vba
Set wins = uia.GetRootElement.FindAll(TreeScope_Children, cond)   ' デスクトップ直下の列挙
m_Title = pick.CurrentName                                        ' 最上位ウィンドウのプロパティ
```

デスクトップ直下を列挙すると、UIA は各最上位ウィンドウのプロバイダへ問い合わせます。
その中には Excel 自身のウィンドウがあり、Excel のプロバイダは**いま呼び出しでブロックして
いるそのスレッド**にいます。互いに待ち合って終わりません。C# 版が同じ列挙を安全にできるのは、
監視を専用の MTA スレッドで回しているからです。VBA には移す先のスレッドがありません。

対処: ウィンドウ列挙は `FindWindowEx` (Win32) で行い、UIA へは `ElementFromHandle` で
1 ウィンドウだけ掴んで入ります。ウィンドウ タイトルも `GetWindowText` から取ります。
**その下の Document 要素のプロパティ読み取りは問題ありません** — 40 ms ごとの
`ValuePattern.CurrentValue` は 1 回 0.05 ms で返ります。この非対称が分かるまでは、
「監視中と表示されたまま何も検知しない」という形で出ます。

### PowerShell の `exit` は引数の式を評価しない

```powershell
exit [SomeType]::Run($a, $b)     # Run が呼ばれないまま終了する
```

`exit [System.Threading.Thread]::Sleep(9000)` が即座に戻ることで確認しました。
`.cmd` が「起動しても何も出ずに終了コード 0」になっていた原因です。
値を受けてから `exit $rc` と書く必要があります。

### VBA の大文字小文字非区別は宣言の途中でも効く

`Private m_bC() As Byte`（表C のバイト列）と `Private m_bc() As Long`（B-C 結合の索引）は
VBA にとって同じ名前です。プロジェクト全体がコンパイル不能になり、自動操作から見える症状は
「マクロを実行できません。このブックでマクロが使用できないか…」だけ、しかも Excel は
見えないダイアログを出して固まります。`build/build_workbooks.ps1` の検査は、
1 行に複数の宣言がある場合と配列宣言 `name() As T` も拾うように直しました。

### Add-Type は日本語リテラルを壊す

`Add-Type -TypeDefinition` はソースを一時ファイルへ書き、同梱の `csc` は BOM の無い
ファイルをシステム ANSI コードページ (ここでは CP932) として読みます。UTF-8 の
「監視中」は CP932 の 3 文字ペアとして取り込まれ、化けたまま画面に出ます。
`build/pack_cmd.ps1` は `.cmd` へ埋め込む時点で U+007F を超える文字をすべて
`\uXXXX` へ書き換えます。逐語的文字列 (`@"..."`) があるとこの置換が壊れるので、
パッカーはそれを見つけたらビルドを止めます。

埋め込む C# は **C# 5 まで**です。同梱の `csc` は文字列補間も `?.` も受け付けません。

### `Worksheets("VIEW")` は「メソッド」ではない

リフレクションの遅延バインドで `InvokeMember(..., BindingFlags.InvokeMethod)` を使うと
`DISP_E_MEMBERNOTFOUND` になります。`Worksheets` は引数つきの propget です。
`BindingFlags.InvokeMethod | BindingFlags.GetProperty` を渡すか、
`Worksheets` を取ってから `Item(name)` を引きます。`WindowState` も同じ理由で
`Set` でなければ通りません。エラー メッセージにメンバー名が入らないので、
COM 呼び出しのラッパー側で名前を添えるようにしました。

### 起動時のメモ帳に前回の番号が残っていると、その場で 1 回走る

各方式の 1 回目は、監視開始の時点でメモ帳に前の実行の番号が残っていたために発火したものです。
仕様どおりの動作 (欄に有効な番号があれば読む) で、処理内容も他の回と同じフル merge-select
なので、そのまま 8 回に含めてあります。

## 5. 計測方法

- 時刻は `QueryPerformanceCounter`。VBA では `Currency` で受けます。VBA の `Timer` は
  `Single` なので、正午過ぎには 1 ULP が 3.9 ms になり 2 ms の表示工程を測れません。
- 引き金は本物です。試験スクリプトはメモ帳へ `WM_CHAR` を 1 文字ずつ 15 ms 間隔で送り、
  アプリは自力で気づきます。エンジンを直接呼ぶ経路では測っていません。
- 工程時間の表示は**計測が終わってから**行います。処理中に状態表示や進捗を書きません。
- 「その他 (差分)」は 合計 − 工程 1〜7 の和です。スレッド間の受け渡しなど、
  どの工程にも属さない時間がここに出ます。隠さずに出しています。
- 失敗した回は失敗として記録します。別方式への切り替えはしません。

再現手順:

```powershell
powershell -ExecutionPolicy Bypass -File build\build_all.ps1
powershell -ExecutionPolicy Bypass -File build\run_bench.ps1 -Method csharp -Repeat 7
powershell -ExecutionPolicy Bypass -File build\run_bench.ps1 -Method vba    -Repeat 7
```

生ログは `work\bench-<方式>-<日時>.tsv` に 1 回 1 行で残ります
(工程別・合計・検知遅延・チェックサム・プローブ数・突合数・検算結果)。

## 6. どれを選ぶか

- **速さだけなら C# 系。** VBA 単独の 5.3 倍。ただし 3.1 秒と 0.6 秒の差が業務上
  意味を持つかは別問題です。カードを読んでから 3 秒で出るなら、実用になる場面はあります。
- **配布のしやすさなら VBA 単独か併用。** VBA 単独はブック 1 冊。併用は 2 ファイルですが、
  画面を Excel で作れるぶん、レイアウト変更に開発環境が要りません。
- **C# 単独の弱点は画面**です。34 ms は問題になりませんが、レイアウトを直すたびに
  ソースを触ってパッケージし直す必要があります。
- **併用の弱点は Excel を 1 つ占有すること**と、スレッド間の受け渡しが 16 ms 見えることです。
  そのかわり、重い処理を Excel の外へ出しつつ画面は Excel のままにできます。

`benchmarks/excel-background-bench` の結論 (「起動手段は効かない、結果の戻し方が効く」) は
ここでも成り立っていますが、**このアプリでは結果が 1 件しかないので、戻し方の差は
34 ms 対 2 ms にしかなりません**。支配的なのは 3 本 241 MB を毎回読み直して
2,000,000 回の突合を行う部分です。1 件を返す経路をいくら磨いても、そこは変わりません。
