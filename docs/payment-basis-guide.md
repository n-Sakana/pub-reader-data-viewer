# 台帳アプリ：①②中心の統合・両方で決済判定・処理済みだけ削除

レイアウト固定版と従来版に、同じ業務条件を反映しています。公開するJSONと入力データは架空の業務サンプルです。個別の本番用JSON・実データは公開していません。

## 使うアプリとJSON

| 版 | ブランチ | サンプル用JSON |
|---|---|---|
| レイアウト固定版 | `semifixed` | `configs/sample/settings.json` |
| 従来版 | `main` | `configs/sample/settings.json` |

配布ZIPは両方ともサンプル設定と入力4本を同梱します。空フォルダへ展開し、`ReaderDataViewer.vbs` を開きます。Windows 64bit、Windows PowerShell 5.1、WPF、WebView2 Runtimeを使います。

本番用には別の空フォルダへ同じ版のZIPを展開し、自分の入力に合わせたJSONをそのフォルダの `settings.json` として置きます。`paths` と実データの配置を確認します。固定版のJSONを従来版へ、またはその逆へ置くことはできません。

今回の「処理済みだけ削除」を使うには、アプリも今回の版に揃えます。以前のアプリにJSONだけを置いても、追加した台帳状態の参照を読めません。

従来版の開発フォルダ直下にある汎用 `settings.json` と作業中の `data/` は保持しています。新しい業務サンプルを試すときは今回のZIPを使います。

## 統合と決済の条件

1. ①の取引IDと②のオーダーIDからカード番号を取り出し、両方に存在する組だけを結合します。
2. その結果へ、②から取り出した申請番号を使って③を左結合します。③がない取引も台帳に残り、③だけの申請は新規追加されません。
3. ①の「【共通】ステータス」が「完了」、かつ②の「決済ステータス」が「決済済」の場合だけ「済」です。片方が未済・空欄・別の値なら、行を残して「未決済」と表示します。
4. ②のオーダーIDを台帳の識別キーとしてマージします。検索と削除の照合には、②から取り出したカード番号・申請番号を使います。③がない行も検索できます。

元の列に加え、①の取引IDと、両方の決済条件を満たした結果を保存する列を追加しています。主画面と候補一覧は同じ決済結果を表示します。未決済時は、従来の表示方針に合わせて申請詳細9項目を空欄にします。③がなくても決済済みなら「済」と表示し、③由来の項目だけ空欄になります。

ここでいう「済」は決済状況、「処理済」は職員がアプリ上で付ける作業状態です。別々に管理します。

## 削除の条件

削除用台帳のカード番号と申請番号が、同じ行の組として統合台帳と一致し、さらにアプリの台帳ステータスが「処理済」の行だけ削除します。カード番号と申請番号が別々の行に存在するだけでは削除しません。

判定するのは、実行時に共有台帳から読み直した保存済みの状態です。手元で「処理済」に変えただけでは対象になりません。「変更をまとめて送信」で保存してから削除します。削除画面にもこの説明を表示します。

## サンプルを実際に使う

同梱の①〜③と削除用ファイルは各100件です。①②の組は100件あり、③と結び付くのは80件。残る20件は③がありません。決済状況は「済」80件、「未決済」20件で、未決済は①だけ未完了10件と②だけ未決済10件です。

| 検索する会員番号 | 確認できること |
|---|---|
| `AA10000000AA` | 決済済み。削除用台帳にも一致する |
| `UQ10005480SY` | ①だけ未完了のため未決済。申請詳細が空欄になる |
| `ZZ20000080ZZ` | ③がなくても検索でき、①②が決済済みなので「済」 |

1. 「データ更新」で100件の統合台帳を作ります。
2. 処理状態を変えずに「データ削除」を実行すると、削除は0件です。
3. `AA10000000AA` を検索し、「未処理」を押して「処理済」にします。この時点で削除しても0件です。
4. 「変更をまとめて送信」を実行します。未送信件数が0件になり、表示がクリアされます。
5. 「データ削除」を実行すると、この1件だけ削除されて99件になります。削除用台帳に一致していても、未処理の19件は残ります。
6. 削除候補20件をすべて処理済みにして送信してから削除する場合は、80件が残ります。その内訳は決済済み60件・未決済20件です。

サンプルは、1申請に複数取引を持たない構成です。検証時だけ2案件に同じカード番号を付け、複数候補の選択経路も確認しています。配布データへこの重複は入れていません。

## JSONのどこを変えるか

| 変更したい内容 | 設定箇所 | 動作の変化 |
|---|---|---|
| 元ファイル名・文字コード・シート・ヘッダー行 | `data.tables` | 読み込む表が変わる。①②はShift_JIS、③は先頭シート、削除用は「リスト_3」 |
| IDから取り出す値 | 更新ジョブ先頭の `calculate` の正規表現 | ①②の照合用カード番号、②の照合用申請番号が変わる |
| ①の決済済みを表す値 | 更新ジョブで `output: mapPaid` の `where.value` | ①で合格する値が変わる。現在は「完了」 |
| ②の決済済みを表す値 | 更新ジョブで `output: payPaid` の `where.value` | ②で合格する値が変わる。現在は「決済済」 |
| 決済済み／未決済の表示文言 | `screen.judgments.paymentStatus.results` | 主画面の表示が変わる。候補一覧の空欄文言も合わせる |
| 削除に使う2項目 | 削除ジョブの `targetMatched` の `keys` | 同じ入力行の2項目で照合する |
| 処理済みの保存値 | `screen.workState.states` と削除ジョブ `targetProcessed` の `where.value` | 両者を同じ値にする。現在は `TRUE` |
| 台帳の保存先 | `paths.ledger` | 別の台帳を使う |
| 台帳に残す項目 | `data.ledger.columns.source` | 保存列が変わる。既存台帳との互換性にも影響する |

たとえば①の列名を「入金確認」、済の値を「確認済」に変えるなら、元CSVの見出しを変え、設定中の `MAP.【共通】ステータス` への参照を `MAP.入金確認` に揃えます。保存列、型、表示名、帳票列などの参照も検索して揃え、`mapPaid` の `where.value` を「確認済」にします。②も同じ要領で変更します。片方の条件を変えても、両方を満たす必要があることは変わりません。

削除の状態条件は次の形です。`$work` は元ファイルの列ではなく、アプリが保存する台帳の処理状態を表します。入力表への参照として使うと設定エラーになります。

```json
{
  "operation": "extract",
  "target1": "ledger",
  "where": { "column": "$work", "operator": "equals", "value": "TRUE" },
  "output": "targetProcessed"
}
```

この抽出結果と2項目一致の抽出結果を `condition: both` で重ね、その結果だけを削除します。状態の表示文字「処理済」を変更しても保存値が `TRUE` のままなら、この条件を変える必要はありません。

設定変更を試すときは、空の別フォルダで新しい台帳を作って確認します。既存台帳がある状態で変更を試す用途ではありません。

## レイアウト固定版と従来版の違い

固定版は、主画面・候補一覧・モーダルの枠や見出し、ボタンの構成を `web/index.html` に置き、余白・幅・文字サイズを `web/fixed.css` で指定します。値との対応は `screen.bindings`、候補の値は `screen.candidates` に残しています。

従来版は `screen.card`、`screen.sections`、`screen.candidates.columns` に画面定義を持ちます。主画面の表示列を変えるときは各行の `value.field`、候補一覧は各列の `value.field` を変更します。

例として「意見欄」に別の保存列を表示する場合、固定版では `screen.bindings.remarks.field`、従来版では意見欄の `textBox` の `value.field` を変更します。固定版で見出しも変えるならHTMLを編集します。従来版はその枠のJSONの `title` も変更します。

固定版の `tools/Convert-Semifixed.py` は、受領済みと同じ画面構成を半固定形式へ変換する道具です。GUI定義を整理するだけで、この業務条件へ自動改定する道具ではありません。このブランチのサンプルJSONには、画面形式と今回の業務変更を反映済みです。

## 既存台帳と残る改定範囲

新しい保存先は `data/ReaderDataViewer-Ledger-PAYMAP.xlsx` です。以前のAPP基準の台帳とは識別キー・保存列が異なるため、別の台帳を作ります。過去データと処理状態の自動移行は含みません。両版の新しい保存形式は一致しています。

現在の再取込は、同じオーダーIDの保存内容が変わると更新し、処理状態を未処理へ戻す設定です。今回の入力結果にない既存行は残します。①②が揃わない行を新規追加しないことと、過去の既存行を消すことは別です。

送信済み行の内容を再取込から保護すること、削除行を丸ごと保管して復元すること、台帳作成後の結合・入力形式の変更を全面禁止することは、今後の改定対象として残っています。現在は削除済み行が再取込で復活し得ます。①だけを選んで取り込む専用処理・UIも今回の変更には含みません。

架空データによるアプリの処理・実画面での操作を確認しています。本番の全レコード、実際の共有先、別端末での操作は未検証です。


## ソースから確認する

従来版は `main`、固定版は `semifixed` を別フォルダへチェックアウトします。個別環境の本番設定は追跡しない `configs/production/` に保管できます。公開サンプルは `configs/sample/settings.json` と `tests/fixtures/sample-v4/` にあります。

業務条件の検査は `powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File tests/Test-PaymentBasis.ps1`、C#回帰は `build.bat test`、配布物の作成は `build.bat package -Theme win98 -RunTests` です。

実画面の操作検査は、従来版が `tests/Test-PaymentLive.ps1`、固定版が `tests/Test-SemifixedLive.ps1`。Node.jsをPATHへ追加するか、`-NodePath` で実行ファイルを指定します。入力は専用フォルダへコピーし、起動した検査用アプリだけ終了します。
