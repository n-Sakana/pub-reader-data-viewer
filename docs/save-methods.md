# 1 件保存の 3 方式比較 (VBA 実用版)

「処理済み」を **1 件、その操作ごとに永続化する**とき、台帳 XLSX へ書き込む方法を 3 つ用意して
同一条件で実測した記録。**配布版の既定は現行方式 (book) のまま**で、この比較のために既定を
変更してはいない (切替は台帳の隣に `<台帳>.savemethod` を置いたときだけで、そのファイルは配布物に含まれない)。

| 方式 | 何をするか | 台帳ブックを開くか |
|---|---|---|
| **book** (現行・配布既定) | 子 Excel (BE) が台帳ブックを開いたまま保持し、対象セルを書いて `Workbook.Save` | 開く (セッション中は開いたまま) |
| **ado** | 閉じた台帳へ ADO/ACE で接続し、対象 1 セルを `UPDATE` する | 開かない |
| **zip** | 閉じた台帳の ZIP を純 VBA で解析し、**元のシート XML の 1 バイトだけ**を書き換えて再構築する | 開かない |

## 測定は 2 つある。混ぜない

| | `bench_e2e.ps1` — **実経路** | `bench_save.ps1` — マイクロ |
|---|---|---|
| 動かすもの | **実配布物**。Excel で `ReaderDataViewer.xlsm` を開き、画面のセルを実マウスでクリックして操作する | 保存関数を直接呼ぶ最小ブック |
| プロセス | 製品と同じ **FE Excel + BE Excel の 2 プロセス** + ファイルチャネル | 1 つ |
| 区間の開始 | **FE が要求ファイルを書いた瞬間** | 保存関数の入口 |
| 区間の終了 | **BE の結果がチャネルに現れた瞬間** | 関数が成功を返した時点 |
| 中に入るもの | 方式固有の処理に加えて、**要求ポーリング (最大 120 ms)・sidecar 書込 (44.6 MB)・publish** | 方式固有の処理だけ |
| 何のための数字か | **人が待つ時間** | 方式そのものの速さ |

以下は**実経路の測定が正本**。マイクロベンチの値 (最大 2,746.1 ms など) は限定条件の参考値で、
実利用の比較には使わない。

# 実経路の測定 (2026-08-15)

再現は `powershell -File build\bench_e2e.ps1`。生ログ `work\bench-e2e-20260815-173030.tsv`、
各試行の FE ログとチャネル追跡は `work\bench-e2e-run\20260815-173030\`。

## 測定単位

アプリのコードは 1 行も変えていない。**外から** `%TEMP%\rdv3` のチャネルを 20 ms ごとに見て、
両端に印を打つ。両端が同じ時計・同じループなので系統誤差 (±1 ポーリング) は打ち消し合う。

- **A 更新確認ジョブ** — 開始 = `rdv3_<sid>_fe_lease.lock` の出現 (`Rdv3HostSpawn` の先頭で作られる
  = FE が BE へ仕事を渡した瞬間) / 終了 = `agg.dat` に CHECK。
  **BE プロセスの起動・ワーカーブックの展開と Open・bootstrap・3 CSV のマージ・保存状態の読込・
  全 10 万行の内容比較**が全部この中にある。
- **A 更新適用ジョブ** (CSV に差分があるとき) — 開始 = FE が `req_decision.dat` (apply) を書いた瞬間 /
  終了 = READY。**引き継ぎ・10 万行 × 29 列の書込・`Workbook.Save`・sidecar 書込**が中にある。
  人が MsgBox に答える時間はこの 2 区間の**間**にあり、どちらにも入らない。
- **B 処理済み登録ジョブ** — 開始 = `req_mark.dat` の出現 ([処理済み] → はい の直後) /
  終了 = `agg.dat` に `res=marked`。**方式固有の初期化・台帳ブックの Open や Close・ADO の接続と
  書き戻しと Close・ZIP の読込と走査と再構築と置換・sidecar 書込**が全部この中にある。

FE の 1 秒 pump は**全方式共通でジョブの外**なので成績に足さない (画面に成功が出るまでの
参考値は別欄)。FE 起動 (Excel 起動 + xlsm Open) も全方式共通でジョブより前なので、
どの方式にも加算せず共通欄に出す。

## 条件

- 日付 / 機械: 2026-08-15、この機。台帳 `ReaderDataViewer-Ledger.xlsx` **24,072,792 バイト /
  100,000 行 × 29 列** (対象シートパートは非圧縮 128,488,013 バイト)、sidecar 44,600,204 バイト。
- **1 試行ごとに配布物一式を新しいコピーへ戻し、新しい Excel プロセス・新しいセッションで開始**。
  方式の切替は `<台帳>.savemethod` だけ。
- 対象は 3 方式で同一の 10 行、順序も同一。画面から 1 件表示になる必要があるので**番号1 が一意の行**を
  等間隔位置の最寄りから選んである: シート行 **14 / 11113 / 22226 / 33334 / 44446 / 55557 / 66668 /
  77779 / 88891 / 100001** (先頭・中間・末尾を含む)。
- 3 条件を混ぜない:
  - **cold** 差分なし起動 → ジョブ A と、**そのセッション最初の**登録 B。試行 i は対象 i。各 10 回。
  - **coldapply** 保存状態が CSV と違う起動 → A(確認) + A(適用) + その後の登録 B。各 10 回。
  - **cont** 1 セッションで**同じ 10 対象を連続登録**。各回は前の保存の確定後に次へ。
- **初回を除外しない。各系列の最大値が成績**。10 値をすべて残す。
- 成功は通知では足りない: 毎回、書き手でも Excel でもない独立リーダー (.NET) でパッケージから
  当該フラグを読み直し、**直前と直後**のパッケージを OOXML 単位で差分検査する。

### コールドの作り方と、その限界

「コールド」は **新しいプロセス + 原本の新しいコピー**という意味。**OS のファイルキャッシュは
落としていない** — 直前のコピー自体がキャッシュを温めるため、落とすには管理者権限のスタンバイ
リスト消去が要り、それは実利用から遠い。この条件は 3 方式で同一だが、**効き方は同じではない**:
台帳ファイル全体を読む zip 方式に最も有利、次に ADO、book は Excel の Open に効く。
実運用で台帳がキャッシュに載っていない場合、**3 方式とも今回より遅くなる**。

## 参考: C# 版 (三方式比較の外)

三方式は VBA 版だけの違いなので、C# 版はこの比較に**入らない** (保存経路が 1 つで差し替えられない)。
ただし「人がどれだけ待つか」の材料として、**同じ 10 対象・同じ 2 つのジョブの定義**で 10 回測った。
C# 版は 1 プロセスで、ジョブの両端はアプリ自身のログ (ミリ秒精度) から取る:
A = `decision check started` (ワーカーへ投入する直前に書かれる) → `decision ready`、
B = `processed save started (exit held...)` → `processed key2=... value=TRUE`。
生ログ `work\bench-e2e-20260815-180902.tsv`。

| 区間 | 最小 | 中央値 | 最大 |
|---|---:|---:|---:|
| A 更新確認ジョブ (差分なし、n=10) | 1,968 | 1,982 | 2,013 ms |
| **B 処理済み登録ジョブ (n=10)** | 623.0 | 627.0 | **635.0 ms** |
| プロセス起動 → 操作可能 (n=10) | 2,779 | 2,797 | 2,940 ms |

- **B の全 10 値**: `630.0 627.0 627.0 627.0 635.0 628.0 628.0 626.0 626.0 623.0`。
  **どの回もほぼ同じ**なのは、C# 版が**毎回 14 MB の台帳を丸ごと書き直す**から。行の深さに依存しない。
- 読み直しは 10/10 成功 (正しい番号1 の行にフラグが付いていることまで確認)。
- **「対象フラグ以外は変えない」契約は 0/10**。C# 版の台帳は処理済みを inline string で持つので、

- C# 版の台帳は 14,138,967 バイト (VBA 版は 24,072,792 バイト)。ジョブ A で sidecar を使わず
  台帳 XLSX 自体を読むので、A は VBA 版 (2.87 秒) より速い 1.98 秒。

  cont では 1 回目だけで、2 回目以降は 1 バイト + `docProps/core.xml`。

## 保存中に何ができるか (補助値、成績ではない)

10 件の連続登録のあと、**同じ検索を 1 回だけ**、アイドル時と「保存要求の 200 ms 後」に実行して
完了時間の差だけを測った (検索要求ファイル出現 → 検索結果がチャネルに現れるまで):

| 方式 | アイドル時 | 保存中 | 増分 |
|---|---:|---:|---:|
| book | 313.7 ms | 1,572.2 ms | **+1,258.5 ms** |
| ado | 348.4 ms | 4,674.1 ms | **+4,325.7 ms** |
| zip | 218.4 ms | 1,606.0 ms | **+1,387.6 ms** |

増分は**その保存の残り時間**にほぼ等しい。BE は 1 本のループなので、保存中に届いた検索は
保存が終わってから答えられる。FE 側 (画面) は別プロセスなので入力自体は受け付ける。

## 人は何秒待つのか (この測定の結論)

**起動してから操作できるまで** (アプリを起動する → 検索できる状態):

| | 差分なし起動 | CSV に差分があり再構築する起動 |
|---|---:|---:|
| VBA 版 | **約 4.6〜5.6 秒** (Excel プロセス起動 1.3 秒 + ブック Open 0.3 秒 + ジョブ A 2.8〜3.0 秒 + pump) | **約 11.5〜12.8 秒** (上記 + 更新適用 6.7〜7.2 秒。人が「はい」を押す時間は別) |
| C# 版 | **約 2.8〜2.9 秒** | (今回未測定) |

**[処理済み] を押してから画面に成功が出るまで** (確認ダイアログに「はい」→ 画面確定、中央値):

| | そのセッション最初の 1 件 | 2 件目以降 |
|---|---:|---:|
| VBA book (現行既定) | **約 4.0 秒** | **約 2.1 秒** |
| VBA ado | 約 5.5 秒 | 約 5.0 秒 |
| VBA zip | 約 1.0 秒 (浅い行) 〜 4.2 秒 (最深行) | 同左 (行の深さで決まる) |
| C# 版 | **約 0.63 秒** | 約 0.63 秒 |

**その間に何ができなくなるか**: 画面 (FE) は別プロセスなので固まらない — 入力も検索の実行も
受け付ける。ただし答えを作る BE は 1 本のループなので、**保存中に投げた検索はその保存が
終わってから答えが返る** (増分 = 保存の残り時間、実測 +1.3〜4.3 秒)。加えて、設計として
**2 件目の [処理済み] は拒否**され、**その保存が確定するまで終了も拒否**される。

**いつ成功を信じてよいか**: 画面が「処理済み: TRUE」に変わったとき。測定中に見つかった
「保存中に検索すると確定表示が出ない」競合は**修正済み** (下記)。修正後は、保存中・保存直前・
保存完了直後のどの順序で検索しても、確定表示も検索結果も失われない (16 回・72 チェック全通過)。

## 実測で見つけた不具合 → 修正済み (2026-08-15)

この測定中に、**保存中に検索を 1 回行うと FE が保存完了通知を取りこぼす**ことが 3 方式 3/3 で
再現した (上表の測定はすべて**修正前**の配布物によるもの)。原因はチャネルが**種別ごとに最新 1 件**
しか持たず、検索応答と保存完了が同じ `RESULT` 種別を共有していたこと。結果として、保存はできて
いるのに終了保護が最大 180 秒 (`MARK_TIMEOUT_S`) 終了を拒み、その後「確定しません」と失敗側で
確定していた。

修正 (Room #62 の指示による): 確定通知に**専用の種別 `MARK`** を与え、`req=<答える要求の版番号>` を
載せて要求と結び付けた。検索の抑制・遅延・リトライはしていない。**16 回・72 チェック全通過**、
終了保留の解除は確定通知から最大 1,463 ms。詳細と証拠は `docs/app.md`
「保存中に検索すると確定通知が消える競合 — 原因と修正」、修正前の証拠は `work\race-evidence-before\`。

この修正は**保存方式そのものには一切触れていない**ので、上の A / B の数値には影響しない
(修正後に同じ `-Mode cont` を回して確認: 最大 3,177.2 ms、読み直し 10/10)。ただし B 区間の終端は
`RESULT res=marked` から `MARK res=marked` に変わっている (同じ瞬間、別スロット)。

## この測定で決めていないこと・限界

- **配布既定は変更していない**。既定は book のまま。切替は `<台帳>.savemethod` を置いたときだけで、
  配布物にそのファイルは無い。BE は起動ログに `savemethod=` を出す。
- OS のファイルキャッシュは落としていない (上記「コールドの作り方と、その限界」)。
- 各条件・各方式 10 回で、run 間の再現性 (同じ系列を日を変えて) は取っていない。
- 上の不具合は**直していない**。測定中に配布物を変えると同条件で揃わなくなるため。
- ハーネスは 33 回、自分が起動した Excel を最後の手段として kill した (毎回、その試行の測定と
  検証がすべて終わったあと)。原因は「FE が自分の遅延クローズを実行している間 `Quit` が無視され、
  無視されても例外にならない」こと。ハーネス側を直した (Quit を繰り返し、プロセスの消滅で確認する)。
  `Excel\Resiliency\DisabledItems` は測定の前後とも空。

# マイクロベンチ (保存関数だけ) — 参考

`bench_save.ps1` の結果。**実利用の比較には使わない**。保存関数の入口から成功復帰までを測るので、
要求ポーリング・sidecar 書込・publish・チャネル往復が入っていない。

## 成績の定義

- 通常の新規セッションで、異なる対象 **10 件を一件ずつ連続**して処理済みにする。
- **初回を含む 10 回のうち最大値が成績**。方式固有の準備 (book の台帳ブック open、ado の provider
  初回接続、zip の deflate 走査) はすべて 1 回目の時間に入る。
- 毎回、前回の保存完了後に次へ進む。まとめ書き・後回しはしない。

## ado の接続の持ち方 (契約下で比較)

毎回 open/close・接続保持・prepared Command・明示 transaction を実測した。
**接続を保持すると 2 件目以降の Execute は 0〜3 ms になるが、それは保存されていないから**である:
接続が開いている間、台帳は**他のプロセスから開けず (ロック)**、変更は Close まで見えない。
つまり保持系は「一件ごとの永続化」を満たさない。**契約を守れるのは毎回 open/close する形だけ**で、
それが上表の 4.5 秒。(`work\ado-probe` の実測: 保持系は 1 回目 ~1,600 ms・以降 0〜3 ms、
独立読取りは `(locked)`。)

# 各方式の実装

## book (現行・配布既定)

`modRdv3Be.DoMark` のまま。BE が台帳ブックを開いたまま保持し、セルを書いて `Workbook.Save`。
Excel の Save は自前の一時ファイル経由なので、保存中に落ちても旧ブックが残る。
**副作用**: セッション中は台帳ファイルが開かれたままで、他のプロセスから読めない。

## ado

```
Provider=Microsoft.ACE.OLEDB.16.0;Data Source=<台帳>;Extended Properties="Excel 12.0 Xml;HDR=NO;"
UPDATE [LEDGER$A{行}:A{行}] SET F1=TRUE
```

- 1 セルだけを範囲で直接指すので、10 万行の走査も他列の型推測も起きない。
- 処理済み列は Excel が**真偽値セル** (`<c t="b">`) で書いているため ACE も boolean と型付けする。
  `SET F1='TRUE'` (文字列) は `-2147217913 抽出条件でデータ型が一致しません` になる。実測で踏んで直した。
- provider は 16.0 → 12.0 の順に開けるほうを使う (同じ ISAM の別名)。どちらも開けない機械では
  **別方式へ黙って切り替えず** `ERR` を返して実測不能と報告する。この機では 16.0 が利用可能。

## zip (純 VBA、外部 EXE も Shell も Win32 も使わない)

`modRdv3Zip`。**元の XML が正本**で、再生成はしない。

- **走査**: deflate はシークできないので、対象行の位置は先頭から復号して見つける。ただし全部を
  作り直す必要はない — 一致 (match) は「長さを足すだけ」で読み飛ばせる。実測 (128 MB、この機):
  読み飛ばし 1,988 ms / 実体化 5,723 ms (呼び出しをインライン化する前は 3,121 / 10,852)。
  32 KB の窓は**先頭から**維持する: 途中から実体化を始めると復元バイトが壊れ、行が見つからない
  (実測)。バイトを「見る」処理だけ、推定位置の手前から有効にする。
- **書換**: 対象セルの値 1 バイトだけを変える。対象ブロックは**自分のハフマンヘッダをビットごと
  そのまま**流用し、シンボル列も元のまま、触るのは対象に触れるシンボルだけ。
- **伝播の遮断**: 後続行の `<v>0</v>` は前の行への match で符号化されているので、1 バイト変えると
  伝播する (実測: 58,033 行のフラグが道連れになった)。対象の 32 KB 以内に始まるブロックは全部
  再生成し、その中で対象バイトを読む match は分割して、そのバイトを**元の値のリテラル**で出す。
- **バイト境界**: deflate はビット列だが、その中の stored ブロックは**バイト境界**にある。残りを
  ビットずらしでコピーすると LEN/NLEN が壊れる (実測: 3 回目の連続パッチで Excel が開けなくなった)。
  再生成は**バイト境界から始まるブロックまで**延ばし、こちら側は空の stored ブロックでバイトに
  揃える。以後は純粋なバイトコピーで済む。
- **CRC-32**: ZIP エントリの CRC は非圧縮側の値だが、CRC-32 は GF(2) 上で線形なので、1 バイト
  差分の補正は 32×32 行列の冪乗 = **O(log n)** で入る (128 MB の再走査なし)。
- **置換**: 既存の `Rdv3ChReplaceFile` (退避→改名→退避破棄、失敗時は復元) をそのまま使う。
- ビルドが毎回自己検査する: CRC-32 の公表チェック値 (`123456789` → `CBF43926`)、1 バイト差分更新と
  全再計算の一致、ビット反転と length/distance 表と RFC 1951 の一致。1 つでも外れたらビルドを止める。
