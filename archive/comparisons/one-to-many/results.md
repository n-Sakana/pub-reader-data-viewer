# 実測結果 — 番号1 が一対多のとき、索引の作り方で何が変わるか

4 方式を、同じ 10 万行 × 3 表、同じ検索キー列、同じ計測区間で比較した記録。

| 方式 | 配布物 | 索引 |
|---|---|---|
| VBA 自前ハッシュ | `dist\ReaderDataViewer-VBA-Hash.xlsm` | バケット連鎖ハッシュ (自作) |
| VBA 標準 Dictionary | `dist\ReaderDataViewer-VBA-Dict.xlsm` | `Scripting.Dictionary` (遅延バインド) の値に `Collection` |
| C# 自前ハッシュ | `dist\ReaderDataViewer-CSharp-Hash.cmd` | バケット連鎖ハッシュ (自作) |
| C# 標準 Dictionary | `dist\ReaderDataViewer-CSharp-Dict.cmd` | `Dictionary<string, List<int>>` |

100 万行・1 対 1 の 3 方式は `docs/results.md` に別記録があり、そちらの配布物・ソースには
今回一切手を触れていない。

## 何を測ったか

番号1 は**正常に一対多**になる。表B は伝票の明細行で、1 つの番号1 が 1・2・3・5 行を
持ちうる。だから番号1 で引くと答えは**集合**になり、利用者が 1 件を選ぶ。

計測区間 (4 方式で同一):

```
t0          番号が確定した瞬間 (メモ帳の 8 桁が 120 ms 安定した時点)
 1..3       表A/B/C を読む
 4..6       表A/B/C の索引を作る          ← 読込と索引を分けて計測している
 7          A-B 結合 (番号1) 表Bの全行
 8          B-C 結合 (番号2) 表Bの全行
 9          番号1 検索 → 候補集合
10          表示準備: 候補 1 件なら統合レコードを画面へ
                     複数件なら候補ダイアログを組み立てて一覧を流し込むまで
── 計測終了 ── 合計 = ここまで。人が選ぶ時間は一切入らない。
(ダイアログ表示)  利用者が読んで選ぶ。計測対象外。
選択後の表示      選んだ候補の統合レコードを描く。別項目として計測。
```

読込と索引作成を分けたのは、**索引に何を使うかがこの比較の全部**だから。

## 索引の値段

読込は方式に依らない (同じ言語なら同じコードが走る)。差が出るのは索引作成 (工程 4-6) と、
索引を引く結合 (工程 7-8) だけ。

| | 索引作成 計 | 結合 計 | 索引まわり 計 | 合計に占める割合 |
|---|---:|---:|---:|---:|
| VBA 自前 | 69.6 | 112.0 | 181.6 | 64% |
| VBA Dict | 605.2 | 717.8 | 1,323.0 | 91% |
| C# 自前 | 3.4 | 18.7 | 22.1 | 25% |
| C# Dict | 26.6 | 38.3 | 64.9 | 44% |

同じ言語で標準の連想配列に替えると、索引まわりは **VBA で 7.3 倍、C# で 2.9 倍**になる。
合計では VBA 5.1 倍、C# 1.7 倍。

1 件あたりに直すと、索引作成は 30 万件で VBA 自前 0.23 µs / VBA Dict 2.0 µs /
C# 自前 0.011 µs / C# Dict 0.089 µs。

理由ははっきりしていて、**キーを文字列にする必要があるかどうか**に尽きる。自前ハッシュは
ファイルのバイト列の上で 8 バイトをそのまま扱う (VBA 版は 8 バイトを Long 2 本に詰めて
比較する)。標準の連想配列はキーが String なので、行ごとに 1 本、探索ごとに 1 本、文字列が
生まれる。100 万行版で `Split` が使えなかったのと同じ話が、規模を変えて出てくる。

### 100 万行版で測った「30 µs/回」との関係

`docs/results.md` には Scripting.Dictionary が 100 万件で約 30 µs/回という実測がある。
今回 10 万件では約 2 µs/回で、**15 倍速い**。件数 10 倍で 1 件あたり 15 倍という非線形が
あるので、「Scripting.Dictionary は遅い」ではなく「**規模で急に遅くなる**」が正しい。
10 万件なら十分実用域 (合計 1.45 秒)、100 万件では実用外 (v1 で読込・索引だけで 28 秒)。

## 一対多の扱い

索引は 4 方式とも `key → 行番号の集合` で、`key → 単一行` の上書き辞書にはしていない。

- 自前ハッシュ: バケット連鎖 (`head[]` / `next[]`)。同じキーの行が連鎖に並ぶだけなので、
  一対多は設計から自然に出る。行が行を上書きする余地がない。
- 標準 Dictionary: C# は `Dictionary<string, List<int>>`、VBA は `Scripting.Dictionary` の
  値に `Collection`。

表A は番号1 が一意なデータだが、索引側はそれを前提にしていない (集合で答え、件数を数える)。
番号2 は一意という前提で扱う。

## 検証

**32 回すべて一致。** 結合チェックサム `46629685`、表B 行数 100,000、A-B 一致 100,000、
B-C 一致 100,000。チェックサムは生成側 (`build\gen_data2.ps1`) が独立に計算して
`data-100k\expected.txt` に書いたものと同じ値。

候補数も 4 方式で完全一致: `00000001`=5、`00001001`=3、`00006001`=2、`00021001`=1。
これは生成時のブロック設計 (キー 1..1,000 が 5 行、1,001..6,000 が 3 行、6,001..21,000 が
2 行、21,001..71,000 が 1 行) から決まる値で、アプリを見ずに分かる。

## 実測で判明した落とし穴

1. **`.cls` は CRLF でないと VBE がクラスヘッダを読まない。** LF だけだと
   `VERSION 1.0 CLASS` 以下をコードとして取り込み、行 1 でコンパイルエラーになる。しかも
   UserForm を足した時点で VBE ウィンドウが開いているので、そのエラーが**モーダル
   ダイアログ**として出て、`Workbook.Save()` が誰も押さない OK ボタンを待って止まる。
   ビルドがハングして見えるが、実体は不可視のダイアログ。
   → `build_workbooks2.ps1` はステージング時に CRLF へ正規化し、フォーム追加直後に
   `VBE.MainWindow.Visible = $false` にする。

2. **デザイン時の MSForms コントロールに `Font` オブジェクトは無い。**
   `$label.Font.Size = 8` は `NullReferenceException`。実行時 (`UserForm_Initialize`) なら
   設定できる。

3. **PowerShell から VBIDE のパラメータ付きプロパティは `Properties('X') = v` で書けない。**
   `Properties.Item('X').Value = v` を使う。

4. **PowerShell 5.1 は BOM 無しのファイルを CP932 として読む。** 日本語を含む .ps1 に BOM が
   無いと、ヒアストリングの終端 `"@` や文字列の引用符が壊れて構文エラーになる (日本語の
   末尾バイトが直後の改行や引用符を食う)。`build\*.ps1` は日本語を含むものすべてに BOM を
   付けてある。

5. **残ったアプリが次の計測に混ざる。** VBA 版は自前のウィンドウを持たず、Excel のタイトルが
   `ReaderDataViewer-VBA-Hash.xlsm - Excel` なので、「Reader Data Viewer ウィンドウが
   残っていないか」の確認をすり抜ける。前の実行で残った 1 つが同じメモ帳を見張り続け、
   こちらが打ち込む番号すべてに対して自分の merge-select を走らせていた。
   → `run_bench2.ps1` は ReaderDataViewer ブックを開いた Excel があれば実行を拒否する
   (自分が起動していない Excel は決して落とさない)。最初の計測一式はこれで汚染されていたので
   破棄し、全 4 方式を取り直した。

6. **`powershell -File` は `-Keys a,b,c` を 1 本の文字列として渡す。** `[string[]]` 引数でも
   分割されない。35 文字の「キー」が打ち込まれ、どの規則にも当たらず時間切れになるだけなので
   気付きにくい。→ スクリプト側でカンマ分割する。

7. **`Timer` は using をまとめると曖昧になる。** `pack_cmd.ps1` は全ソースの using を 1 つに
   束ねるので、`System.Threading.Timer` と `System.Windows.Forms.Timer` が衝突する。
   完全修飾で書く。

8. **WinForms のモーダルダイアログは UIA ツリー上でオーナーの「子孫」に出る。**
   デスクトップ直下を走査しても見つからない。自動確認を書くときに引っかかる。

## 再現手順

```powershell
powershell -File build\gen_data2.ps1                          # 10 万行 × 3 表
powershell -File build\gen_data2.ps1 -Rows 200 -OutDir data-tiny
powershell -File build\build_all2.ps1 -SkipData               # 4 配布物
powershell -File build\run_bench2.ps1 -Method chash -Repeat 8
powershell -File build\run_bench2.ps1 -Method cdict -Repeat 8
powershell -File build\run_bench2.ps1 -Method vhash -Repeat 8
powershell -File build\run_bench2.ps1 -Method vdict -Repeat 8
```

各実行は `work\bench2-<方式>-<日時>.tsv` を残し、`summarize2.ps1` が中央値を出す。
`-AutoPick <n>` は候補ダイアログを自動で答える (計測終了後に効くので数値には入らない)。
人が操作するときは付けないか `-AutoPick -1`。

計測環境: Windows 11 Home 10.0.26200 / Excel 64bit / Windows PowerShell 5.1。
